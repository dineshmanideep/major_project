      ## 2. Objective-by-Objective Implementation Breakdown
      
      ### Objective 1 — Extend one-to-one E2E to hierarchical group-wise E2E
      This is the umbrella objective, realized by wiring Objectives 2, 3, and 4 together around the baseline AES-GCM payload pipeline from Amirkhanova et al.
      
      **Components to build:**
      - Publisher module (ESP32): topic-key lookup → AES-256-GCM encrypt (adapted from the Paper 1 baseline)
      - Subscriber/gateway module (Raspberry Pi): topic-key lookup (via Objective 2's derivation) → AES-256-GCM decrypt → whitelist check
      - No crypto logic on the broker — it stays a pure, unmodified Mosquitto relay
      
      **Tasks:**
      1. Port/replicate Paper 1's AES-GCM pipeline on ESP32 (mbedTLS) as the payload baseline.
      2. Replace the single pre-shared-key lookup with a call into the key-derivation module (`get_key(topic)` instead of a hardcoded key).
      3. Support multiple simultaneous publishers on different leaf topics under one branch — no new logic needed beyond per-topic key lookup, but requires testing with 2+ ESP32 boards publishing concurrently.
      4. Build a gateway-side multi-subscriber test harness (simulate a dashboard, a historian, and a vendor subscribing to overlapping branches of the topic tree).
      
      **Validation:** publish under a branch, confirm every intended subscriber decrypts successfully, and confirm a subscriber scoped to a different branch cannot.
      
      ---
      
      ### Objective 2 — Topic-hierarchical key derivation
      **Components to build:**
      - KDF module: HKDF (HMAC-SHA256-based), implemented identically on ESP32 (mbedTLS HKDF, or hand-rolled HMAC-based KDF) and Raspberry Pi (Python `cryptography` library's HKDF)
      - Topic-tree key cache: a local map from topic path → derived key, populated **lazily** (derive-on-demand, then cache) rather than precomputing the whole tree
      - API: `get_key(topic_path, held_ancestor_key, held_ancestor_path)` — walks the remaining path segments, applying the KDF repeatedly
      
      **Tasks:**
      1. Define a canonical label encoding for each topic segment (deterministic byte encoding, e.g. UTF-8 bytes of the segment name) to feed into the KDF as the "info"/context parameter.
      2. Implement `derive_child_key(parent_key, child_label) → child_key` using HKDF-Expand (parent key as PRK, child label as info).
      3. Implement the path-walking derivation function: given a held key for some ancestor node, compute any descendant's key by applying step 2 repeatedly along the path.
      4. Unit tests: confirm derived keys are deterministic and stable, and confirm ESP32 and Raspberry Pi implementations produce **identical** keys for the same path (cross-platform correctness is critical here).
      5. Security check: confirm, by code review and a documented argument (not yet a formal proof), that there is no feasible path from a child key back to its parent.
      
      **Validation:** cross-platform unit tests on identical inputs; a deliberate "attempt to derive upward" test that is expected to fail.
      
      ---
      
      ### Objective 3 — Tree-based, lazily-triggered rekeying
      **Components to build:**
      - A small **key-controller service**, co-located with the Raspberry Pi gateway (not the untrusted broker), tracking per-branch state: `{branch_path: {key_version, stale, last_rekey_time}}`
      - Revocation API: `revoke(device_id, branch_path)` — removes the device from the branch's authorized list and sets `stale = True`
      - Lazy trigger hook: inserted into the publish-handling path — before a message is accepted/forwarded on a branch, check its `stale` flag; if stale, regenerate and redistribute the branch's key to remaining authorized members **first**, then proceed
      - Bounded staleness timer: a background check (e.g. every N minutes) that forces a rekey if a branch has been `stale` for longer than a configured maximum, even with no pending publish
      
      **Tasks:**
      1. Implement the key-controller service and its branch-state table.
      2. Implement the revocation API.
      3. Implement the lazy trigger hook in the publish path.
      4. Implement the bounded staleness timer as a background task.
      5. Confirm path-confinement: rekeying branch X must only regenerate X's key (and, by Objective 2's derivation, X's descendants) — siblings must remain untouched. This should fall out "for free" from the derivation design, but needs an explicit test.
      
      **Validation:** simulate a revocation on an idle branch (confirm no rekey happens until the next publish or the staleness timeout); simulate a revocation on an active branch (confirm rekey completes before the next message is exposed); measure keys regenerated per revocation against tree depth.
      
      ---
      
      ### Objective 4 — Post-quantum-secured key establishment
      **Components to build:**
      - liboqs cross-compiled for ESP-IDF (ESP32 side) and available via liboqs-python or C bindings (Raspberry Pi side) — **flagged as the highest-risk integration task**
      - ML-KEM handshake flow: device generates an ML-KEM keypair → publishes its public key → gateway/key-controller encapsulates against it and returns the ciphertext → device decapsulates → the resulting shared secret becomes the root key seed fed into Objective 2's derivation chain
      - Device identity check integrated at this step, reusing Paper 1's whitelist/AAD approach
      
      **Tasks:**
      1. Cross-compile liboqs for the ESP-IDF toolchain.
      2. Define the handshake message format (device public key, encapsulated ciphertext, device ID), carried as ordinary MQTT messages on a dedicated bootstrap topic (e.g. `_bootstrap/<device_id>`).
      3. Implement the handshake state machine on both ends.
      4. Feed the resulting shared secret into Objective 2's KDF as the root key for the device's authorized branch.
      5. Benchmark handshake latency and message size against the classical ECDH baseline.
      
      **Validation:** end-to-end handshake test (a fresh device boots, completes the handshake, and successfully derives and uses topic keys); latency/size benchmarking against the Amirkhanova baseline.

        ## How to implement each methodology
      
        ### 1. Hierarchical group E2E encryption
      
        Implement this first as the working baseline.
      
        - ESP32 reads a sensor value.
        - It gets the symmetric key for its exact topic.
        - It encrypts once using AES-256-GCM.
        - It publishes an envelope to MQTT.
        - Every authorised subscriber derives the same topic key and decrypts locally.
        - The broker forwards unchanged ciphertext only.
      
        Suggested envelope:
      
        {
          "v": 1,
          "key_version": 4,
          "sender_id": "esp32-oven-01",
          "nonce": "base64-encoded 96-bit nonce",
          "ciphertext": "base64-encoded encrypted payload",
          "tag": "base64-encoded GCM tag"
        }
      
        Use MQTT topic and selected metadata as AES-GCM AAD:
      
        AAD = protocol_version || mqtt_topic || key_version || sender_id
      
        This prevents an attacker from moving valid ciphertext from one topic/device context to another.
      
        ### 2. Topic-hierarchical key derivation
      
        Use HKDF-SHA-256 to derive child keys deterministically.
      
        K(child) = HKDF-Expand(
          PRK  = K(parent),
          info = "MP1/topic/v1/" || UTF-8(child_segment),
          L    = 32 bytes
        )
      
        For this topic tree:
      
        factory
        └── line3
            ├── oven
            │   └── temp
            └── motor
                └── speed
      
        a dashboard authorised for factory/line3 holds K(line3) and can derive:
      
        K(line3/oven)
        K(line3/oven/temp)
        K(line3/motor)
        K(line3/motor/speed)
      
        A vendor authorised only for factory/line3/motor holds K(motor) and can derive K(speed), but cannot derive K(line3) or oven keys.
      
        ### 3. Tree-based lazy rekeying
      
        Keep branch membership and versions in the Key Controller.
      
        branch                    version   stale   authorised members
        factory/line3             4         false   gateway, dashboard
        factory/line3/motor       7         false   gateway, vendor
      
        On revocation:
      
        1. Remove the device from the branch membership list.
        2. Mark the affected branch stale.
        3. Do not immediately interrupt a silent branch.
        4. Before the next publish to that branch, generate a fresh branch root key and increment its version.
        5. Securely distribute the new key only to remaining authorised members.
        6. The publisher uses the new version before its payload is accepted/published.
        7. Force rekey after a maximum staleness timeout even if the branch is idle.
      
        For the first prototype, make this simple and correct: rekey the revoked branch and all descendants. Optimise to full Logical Key Hierarchy distribution only
        after the baseline works. The relevant security property is that no message is sent under an old key after the rekey commit.
      
        ### 4. Post-quantum ML-KEM onboarding
      
        Use ML-KEM only when a device joins or receives refreshed branch-key material; continue using AES-256-GCM for every telemetry packet.
      
        1. Device boots with an identity credential.
        2. It generates an ML-KEM keypair.
        3. It sends its public key to _bootstrap/<device-id> through MQTT.
        4. Key Controller verifies the device identity and its permitted branch.
        5. Controller encapsulates to the device’s ML-KEM public key.
        6. Device decapsulates the ciphertext; both obtain the same shared secret.
        7. Derive an encrypted key-distribution session key from that shared secret.
        8. Controller sends the authorised branch key/version encrypted under that session key.
        9. Device derives leaf-topic keys locally.
      
        Use a signed controller response or a pre-provisioned controller public key, otherwise a malicious broker could impersonate the controller during bootstrap.

        ### Module API
      
        derive_child_key(parent_key, child_label) -> 32-byte key
      
        derive_topic_key(
            held_key,
            held_path,
            requested_topic

        - Split topics only by /.

        - Define whether topic names are case-sensitive; MQTT normally is, so retain case.
        - Include a fixed protocol/version label in HKDF info.
        - Do not concatenate ambiguous text directly; length-prefix each segment.
      
        A safe info encoding is:
      
        "MP1-KDF-v1" || uint16_be(length(segment)) || UTF-8(segment)

      """Deterministic, one-way topic-hierarchical key derivation.
      
      This is a dependency-free reference implementation intended to match an
      ESP32/mbedTLS HKDF-Expand implementation byte-for-byte.  It does not perform
      key distribution: callers must provision an authorised ancestor key securely.
      """
      
      from __future__ import annotations
      
      import hashlib
      import hmac
      
      
      KEY_LENGTH = 32  # AES-256 key size
      _DOMAIN = b"MP1-TOPIC-KDF-v1"
      
      
      class TopicKeyError(ValueError):
          """Raised when a topic path is malformed or outside an authority scope."""
      
      
      def _segments(path: str) -> tuple[str, ...]:
          """Return a validated canonical MQTT topic path as individual segments."""
          if not isinstance(path, str) or not path:
              raise TopicKeyError("topic path must be a non-empty string")
          parts = tuple(path.split("/"))
          if any(not part for part in parts):
              raise TopicKeyError("topic path must not contain empty segments")
          if any("+" in part or "#" in part for part in parts):
              raise TopicKeyError("wildcards are not valid cryptographic topic paths")
          return parts
      
      
      def _encode_info(segment: str) -> bytes:
          """Use an unambiguous, versioned HKDF info encoding for one segment."""
          encoded = segment.encode("utf-8")
          if len(encoded) > 65535:
              raise TopicKeyError("topic segment is too long")
          return _DOMAIN + len(encoded).to_bytes(2, "big") + encoded
      
      
      def derive_child_key(parent_key: bytes, child_segment: str) -> bytes:
          """Derive a 32-byte child key using one block of HKDF-Expand/SHA-256.
      
          ``parent_key`` is treated as the 32-byte HKDF pseudorandom key (PRK).
          The byte ``0x01`` is HKDF-Expand's counter for its first output block.
          """
          if not isinstance(parent_key, bytes) or len(parent_key) != KEY_LENGTH:
              raise TopicKeyError("parent key must be exactly 32 bytes")
          _segments(child_segment)  # applies the same segment validation rules
          if "/" in child_segment:
              raise TopicKeyError("child segment must not contain '/'")
          return hmac.new(parent_key, _encode_info(child_segment) + b"\x01", hashlib.sha256).digest()
      
      
      def derive_topic_key(held_key: bytes, held_path: str, requested_topic: str) -> bytes:
          """Derive a descendant's key, rejecting parent and sibling access attempts."""
          ancestor = _segments(held_path)
          target = _segments(requested_topic)
          if len(target) < len(ancestor) or target[: len(ancestor)] != ancestor:
              raise TopicKeyError("requested topic is outside the held branch")
      
          key = held_key
          for segment in target[len(ancestor) :]:
              key = derive_child_key(key, segment)
          return key
      """AES-256-GCM envelopes for MQTT payloads.
      
      The MQTT topic is deliberately authenticated but is not included in the JSON
      envelope: MQTT already carries it for routing.  A relay that changes a message's

              raise EnvelopeError("tag must be 16 bytes")

              raise EnvelopeError("message authentication failed") from exc

            self.max_staleness = max_staleness

            _validate_branch_path(branch_path)

    # MP-1 Secure MQTT Prototype
    
    This repository contains a Python reference implementation of encrypted,
    topic-hierarchical MQTT telemetry. The MQTT broker is an untrusted relay: it
    receives MQTT topic names and encrypted bytes, but never application plaintext
    or topic-key material.
    
    ## Implemented features
    
    ### 1. Topic-hierarchical key derivation
    
    **Code:** `src/topic_keys.py`
    
    This module creates a separate 32-byte AES-256 key for every concrete MQTT
    topic, starting from a securely provisioned branch key.
    
    - `derive_child_key(parent_key, child_segment)` derives one child key with
      HKDF-Expand/HMAC-SHA-256.
    - `derive_topic_key(held_key, held_path, requested_topic)` walks from an
      authorised ancestor to a requested descendant topic.
    - A holder of `factory/line3` can derive keys such as
      `factory/line3/oven/temp` and `factory/line3/motor/speed`.
    - A holder of `factory/line3/motor` can derive motor descendants but cannot
      derive an oven key, its parent key, or a sibling branch key.
    - Key derivation uses a domain-separated, length-prefixed label encoding:
      `MP1-TOPIC-KDF-v1 || uint16_be(segment_length) || UTF-8 segment`.
    - Empty segments, MQTT wildcards (`+` and `#`), non-string paths, oversized
      segments, parent requests, and sibling requests are rejected.
    - A fixed derivation vector is tested so a future ESP32/mbedTLS port can match
      the Python output byte-for-byte.
    
    ### 2. AES-256-GCM telemetry encryption
    
    **Code:** `src/message_envelope.py`
    
    Every sensor payload is encrypted using the AES-256 key derived for its exact
    MQTT topic.
    
    - `encrypt_payload(...)` derives the topic key, creates a random 96-bit nonce,
      and produces an AES-256-GCM envelope.
    - `decrypt_payload(...)` derives the same key for an authorised consumer and
      verifies then decrypts the envelope.
    - The envelope includes `protocol_version`, `key_version`, `sender_id`,
      Base64 `nonce`, Base64 `ciphertext`, and Base64 authentication `tag`.
    - The plaintext is encrypted; the MQTT topic is intentionally not placed in
      the payload because MQTT already provides it for routing.
    - AES-GCM additional authenticated data binds the protocol version, MQTT
      topic, sender ID, and key version to the ciphertext. A relay cannot move a
      valid message to another topic, alter its claimed sender, or change its key
      version without authentication failure.
    - `serialise_envelope(...)` produces compact JSON bytes suitable for an MQTT
      payload; `parse_envelope(...)` validates and parses received JSON.
    - The implementation validates exact fields, protocol version, Base64 fields,
      nonce length, tag length, and authentication tag before returning plaintext.
    
    ### 3. Encrypted MQTT publisher and subscriber prototype
    
    **Code:** `src/mqtt_prototype.py`
    
    This is the first end-to-end application layer over the encryption modules.
    
    - `EncryptedPublisher` accepts sensor bytes, derives the exact topic key,
      encrypts once, serialises the envelope, and publishes only ciphertext bytes.
    - `EncryptedSubscriber` subscribes to `held_path/#`, derives authorised topic
      keys locally, and stores successfully decrypted `(topic, plaintext)` pairs.
    - Invalid, malformed, and unauthentic received messages are recorded in the
      subscriber's `rejected` list rather than being exposed as telemetry.
    - `InMemoryBroker` simulates an untrusted MQTT broker for deterministic tests.
      It only forwards topic names and byte payloads; it does not know keys or
      perform decryption.
    - `PahoMqttTransport` is a live adapter for a Mosquitto-compatible broker,
      using the `paho-mqtt` package. The caller subscribes first, then runs its
      MQTT client network loop.
    
    ### 4. Multiple authorised subscribers
    
    **Code:** `tests/test_mqtt_prototype.py`
    
    The prototype demonstrates group-style encrypted delivery.
    
    - A publisher encrypts one envelope for `factory/line3/oven/temp`.
    - Two separate authorised consumers, such as a dashboard and historian, use
      their `factory/line3` branch key to decrypt that exact same ciphertext.
    - A motor-only consumer is subscribed only to `factory/line3/motor/#`; it does
      not receive oven telemetry and its key cannot derive an oven-topic key.
    - A malformed/tampered transport payload is rejected by the receiver.
    
    ### 5. Trusted Key Controller and branch membership
    
    **Code:** `src/key_controller.py`
    
    `KeyController` represents the trusted service that owns membership and branch
    root keys. It is intentionally separate from the MQTT broker.
    
    - `create_branch(branch_path, members, root_key=None)` creates a managed branch
      with a random 32-byte root key by default and version `1`.
    - `add_member(device_id, branch_path)` authorises a device, gateway, or
      consumer for that branch.
    - `credential_for(device_id, branch_path)` returns the member's current
      `BranchCredential`: branch path, current root key, and key version.
    - Unauthorised members and unknown branches are rejected with
      `KeyControllerError`.
    - `branch_status(branch_path)` exposes safe operational state—members,
      key-version, stale flag, and last rekey time—without exposing the root key.
    - In this Python prototype, credential retrieval models a secure controller to
      device distribution channel. Authenticating and encrypting that distribution
      channel with ML-KEM is not implemented yet.
    
    ### 6. Lazy, branch-confined revocation rekeying
    
    **Code:** `src/key_controller.py`, `src/managed_mqtt.py`
    
    Revocation is implemented as lazy rekeying for one managed branch.
    
    - `revoke(device_id, branch_path)` immediately removes the member and marks
      only that branch as stale. It does not rotate the key at revocation time.
    - On the next authorised `credential_for(...)` request, the controller creates
      a fresh random 32-byte branch root key, increments `key_version`, clears the
      stale state, and records the rekey time.
    - A revoked member cannot obtain the new credential. Its old root key cannot
      authenticate or decrypt messages encrypted after the rotation.
    - `rekey_expired()` forces rotation for stale idle branches after the configured
      `max_staleness` period, so a silent branch cannot remain stale indefinitely.
    - Rekeying is confined to the affected configured branch. For example,
      revoking a member of `factory/line3/motor` rotates motor and its descendants;
      a separately managed `factory/line3/oven` branch retains its root key and
      version.
    
    ### 7. Controller-managed MQTT endpoints
    
    **Code:** `src/managed_mqtt.py`
    
    These helpers combine the Key Controller with encrypted MQTT operations.
    
    - `ControllerManagedPublisher` asks the controller for its current credential
      immediately before each encryption. Therefore, a stale branch is rekeyed
      before the next ciphertext is published.
    - The current credential's `key_version` is embedded in the AES-GCM envelope,
      so recipients authenticate both the ciphertext context and its key version.
    - `ControllerManagedSubscriber` obtains its current credential before
      decrypting. Once revoked, it can no longer retrieve the rotated key and does
      not expose subsequent telemetry.
    - The integration test verifies a gateway receives messages before and after
      rotation, while a revoked vendor receives only the pre-revocation message.
    
    ## Security properties tested
    
    **Test files:** `tests/test_topic_keys.py`, `tests/test_message_envelope.py`,
    `tests/test_mqtt_prototype.py`, and `tests/test_key_controller.py`.
    
    - Deterministic cross-platform KDF test vector.
    - Different sibling topic labels derive different keys.

    - Idle stale branches are rekeyed at their configured deadline.

## Lazy branch rekeying strategy

The system does not immediately generate a new key when a member is revoked. Instead, it marks only the affected branch as “stale,” then rotates that branch key at the next safe trigger.

This avoids unnecessary work for inactive branches while ensuring no new message is encrypted with the old branch key after rekeying begins.

Example branches:

```text
factory/line3/oven
factory/line3/motor
```

If a vendor is revoked from `factory/line3/motor`, only the motor branch rotates. The oven branch keeps its existing key and version.

### Branch state

Each managed branch in `KeyController` stores:

```python
@dataclass
class _BranchState:
    root_key: bytes
    key_version: int = 1
    members: set[str] = field(default_factory=set)
    stale_since: datetime | None = None
    last_rekey_at: datetime | None = None
```

Meaning:

- `root_key`: current 32-byte key for the branch.
- `key_version`: increments every time the branch root key changes.
- `members`: devices/consumers allowed to obtain the current branch credential.
- `stale_since`: set when a member is revoked; means rotation is required.
- `last_rekey_at`: operational record of the latest completed rotation.

A `BranchCredential` supplied to an authorised device contains:

```python
@dataclass(frozen=True)
class BranchCredential:
    branch_path: str
    root_key: bytes
    key_version: int
```

The device uses `root_key` as its held ancestor key and derives keys for individual descendant topics.

## 6. Bounded staleness for idle branches

A lazy strategy needs a maximum delay. Otherwise, a revoked branch that never publishes again could remain stale forever.

The controller has a configurable limit:

```python
controller = KeyController(
    max_staleness=timedelta(minutes=5)
)
```

A scheduler/background task periodically calls:

```python
rekeyed = controller.rekey_expired()
```

The relevant logic is:

```python
def rekey_expired(self, *, now=None) -> list[str]:
    current_time = now or _now()
    rekeyed = []

    for path, state in self._branches.items():
        if (
            state.stale_since is not None
            and current_time - state.stale_since >= self.max_staleness
        ):
            self._rekey(state, current_time)
            rekeyed.append(path)

    return rekeyed
```

Timeline:

```text
10:00  Vendor revoked from motor branch
       motor branch becomes stale

10:03  No publish occurs
       branch remains stale; no rotation yet

10:05  Scheduler calls rekey_expired()
       branch root key rotates from K_motor_v1 to K_motor_v2

10:10  A future publisher retrieves version-2 credentials
       next telemetry uses K_motor_v2-derived topic keys
```

## 7. Branch confinement

The rekey operation changes only the exact managed branch state:

```python
state = self._state(branch_path)
self._rekey(state, current_time)
```

It does not iterate across all branches or alter siblings.

Example:

```text
factory/line3/motor  → vendor revoked → version 1 → version 2
factory/line3/oven   → unaffected     → stays version 1
```

The test verifies this directly:


A rekey has two separate key operations:

1. Generate a new branch root key.
2. Derive new per-topic keys from that new root key.

You must not derive the new branch root key from the old root key, because the revoked user knows the old root key and could derive it too.

### 1. New branch root key

Current implementation generates a cryptographically random 32-byte key:

```python
state.root_key = secrets.token_bytes(KEY_LENGTH)
state.key_version += 1
```

For example:

```text
Before revocation:
K_motor_v1

After rekey:
K_motor_v2 = random 32-byte key
```

`K_motor_v2` is independent of `K_motor_v1`. A revoked vendor holding version 1 cannot calculate version 2.

### 2. New leaf-topic key derivation

Once authorised users have the new branch root key, they derive their normal topic keys again.

For topic:

```text
factory/line3/motor/speed
```

Before rotation:

```text
K_speed_v1 = HKDF-Expand(K_motor_v1, "speed")
```

After rotation:

```text
K_speed_v2 = HKDF-Expand(K_motor_v2, "speed")
```

The publisher encrypts with `K_speed_v2`; authorised consumers derive `K_speed_v2` and decrypt.

## What production delivery should do

The Key Controller should securely send the new branch credential separately to every remaining authorised device.

Conceptual flow:

```text
1. Revoke vendor from motor branch.
2. Mark motor branch stale.
3. On next publish, generate K_motor_v2.
4. For each remaining member:
     - establish/authenticate a secure session
     - encrypt K_motor_v2 and version 2 for that member
     - send the key-update message
5. Publisher encrypts telemetry with keys derived from K_motor_v2.
6. Revoked vendor cannot decrypt because it never received K_motor_v2.
```

A key-update payload could look like:

```json
{
  "type": "branch_key_update",
  "branch": "factory/line3/motor",
  "key_version": 2,
  "encrypted_branch_key": "..."
}
```

It could be routed through MQTT, for example:

```text
_bootstrap/motor-01/key-update
_bootstrap/gateway/key-update
```

The untrusted broker can forward those encrypted messages, but must not see the new branch key.

## How to encrypt the new key for each user

The planned ML-KEM onboarding feature provides this secure distribution mechanism.

For each remaining user:

```text
Device and Key Controller establish ML-KEM shared secret
                    ↓
Derive a session encryption key
                    ↓
AES-GCM encrypt K_motor_v2 for that device
                    ↓
Publish encrypted key-update message
                    ↓
Device decrypts and stores K_motor_v2
```

Conceptually:

```python
session_key = hkdf(ml_kem_shared_secret, info=b"MP1-key-update-v1")

    branch_root_key_v2,
    aad=b"factory/line3/motor|version=2",

```

The controller must perform this once per remaining authorised device, because each device should have its own protected key-distribution session.

      Conclusion
      
      This report has surveyed the literature on end-to-end encrypted MQTT for Industrial

      def _matches(topic_filter: str, topic: str) -> bool:
          """Match exact topic filters and the MQTT multi-level ``#`` wildcard."""
          filter_parts = topic_filter.split("/")
          topic_parts = topic.split("/")
          if not topic_filter or any(not part for part in filter_parts):
              raise ValueError("topic filter must not contain empty segments")
          if filter_parts[-1:] == ["#"]:
              if any(part in {"#", "+"} for part in filter_parts[:-1]):
                  raise ValueError("only a trailing # wildcard is supported")
              return topic_parts[: len(filter_parts) - 1] == filter_parts[:-1]
          if any(part in {"#", "+"} for part in filter_parts):
              raise ValueError("only a trailing # wildcard is supported")
          return filter_parts == topic_parts
      
      
      @dataclass
      class InMemoryBroker:
          """An untrusted relay simulation: it stores only topic names and bytes."""
      
          subscriptions: list[tuple[str, MessageHandler]] = field(default_factory=list)
      
          def publish(self, topic: str, payload: bytes) -> None:
              for topic_filter, handler in tuple(self.subscriptions):
                  if _matches(topic_filter, topic):
                      handler(topic, payload)
      
          def subscribe(self, topic_filter: str, handler: MessageHandler) -> None:
              _matches(topic_filter, "_validation") if topic_filter == "#" else _matches(topic_filter, topic_filter.rstrip("/#") or "_")

      @dataclass
      class EncryptedPublisher:
          """Encrypt sensor bytes once and publish only the resulting envelope."""
      
          transport: MqttTransport
          sender_id: str
          held_key: bytes
          held_path: str
          key_version: int
          _sequences: dict[str, int] = field(default_factory=dict)
      
          def publish(self, topic: str, plaintext: bytes) -> dict[str, Any]:
              sequence = self._sequences.get(topic, 0) + 1
              envelope = encrypt_payload(
                  plaintext,
                  topic,
                  self.held_key,
                  self.held_path,
                  self.sender_id,
                  self.key_version,
                  sequence,
              )
              self._sequences[topic] = sequence
              self.transport.publish(topic, serialise_envelope(envelope))
              return envelope
      
      
      @dataclass
      class EncryptedSubscriber:
          """Subscribe to an authorised branch and decrypt messages locally."""
      
          transport: MqttTransport
          held_key: bytes
          held_path: str
          received: list[tuple[str, bytes]] = field(default_factory=list)
          rejected: list[tuple[str, str]] = field(default_factory=list)
          replay_protector: ReplayProtector = field(default_factory=ReplayProtector)
      
          def subscribe(self) -> None:
              """Subscribe exactly to the subtree represented by the held key."""
              self.transport.subscribe(f"{self.held_path}/#", self._handle_message)
      
          def _handle_message(self, topic: str, payload: bytes) -> None:
              try:
                  envelope = parse_envelope(payload)
                  plaintext = decrypt_payload(envelope, topic, self.held_key, self.held_path)
                  self.replay_protector.accept(
                      topic, envelope["sender_id"], envelope["key_version"], envelope["sequence"]
                  )
              except EnvelopeError as exc:
                  self.rejected.append((topic, str(exc)))
                  return
              self.received.append((topic, plaintext))
      
          def can_decrypt(self, topic: str) -> bool:
              """Return whether the subscriber's ancestor key authorises ``topic``."""
              try:
                  derive_topic_key(self.held_key, self.held_path, topic)
              except TopicKeyError:
                  return False
              return True
